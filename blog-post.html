I Programmed an AI in 6502 Assembly. It Worked.

In 1975 the 6502 moved bytes in and out of memory. A Claude Code skill now uses the same mnemonics to move forge tickets in and out of a triage loop. Same verbs, bigger nouns.

I'll be honest, this started as a joke. I wanted to see if I could get Claude Code to respond entirely in 6502 assembly language. The 6502 powered the Apple II, the Commodore 64, the BBC Micro, the NES. It had 56 opcodes, 64KB of address space and absolutely no business being anywhere near a large language model.

So obviously I built a Claude Code skill that maps its instruction set onto a modern triage-and-fix workflow. You write .s files. Claude executes them. Its response is also assembly. There's a zero-page. There's a stack. BRK means "commit and halt."

It's not a real 6502, of course. I borrowed the mnemonics. The chip is fictional; the mnemonics are legendary.

And then something unexpected happened. The trace it produced wasn't just a joke output. It was a working triage policy expressed as a program — not a prompt — that I could re-run, version, audit, and reason about as code. The 6502 borrow gave me discipline I hadn't realised I needed.

Opcode Oriented Programming (OOP) 😄
6502 mnemonics. Modern AI execution. Workflows as programs.

The Trace Is the Reply

An 800-token prose response ("Let me analyse this issue. I'll start by examining the file at...") becomes a handful of lines of assembly trace. Issue fetched, file fixed, tests passed, diff reviewed, committed, PR opened. No "Let me now...", no "I'll proceed to...", no "Here's what I did...". Just the trace.

That trace is structured. Diffable. Greppable. Re-runnable. Whether it costs fewer tokens than prose turned out to be more complicated than I expected (more on that below) — but the structural value lands regardless.

How It Works: 15 Opcodes and 9 Vectors

The skill is called opcode and it defines a semantic DSL that borrows the 6502's mnemonics but maps them onto issue triage. The core ISA is just 15 opcodes. You can genuinely hold the entire thing in your head.

LDA loads an issue. STA persists to a slot. LDX/INX/CPX handle loops. JSR calls one of nine I/O vectors: FETCH, FIX, TEST, LINT, REVIEW, PUSH, PULL, CLONE, ANALYZE. BCC/BCS branch on test results. BRK commits and halts. PHA/PLA push and pop todos from a stack that maps directly to Claude Code's task list.

There's a zero-page with named slots. $00 is the current issue ID, $01 is the branch name, $02 is the current file, $05 is the commit message. The fetched issue queue lives at $10-$1F. The stack page at $0100-$01FF is the Claude Code task list.

It talks to GitHub or GitLab through a forge abstraction layer so JSR PUSH opens a PR on GitHub or an MR on GitLab. Nobody has to compromise their vocabulary.

The Smallest Useful Program

Six opcodes, three flags in play. This is the heart of what the whole thing does:

        .ORG    $0600
        LDA     #$2A        ; issue 42, Hex is not mandatory
        JSR     FETCH
        JSR     FIX
        JSR     TEST
        BCC     skip        ; tests failed → bail
        BRK                 ; commit + halt
skip:   RTS                 ; leave uncommitted

If the tests pass (C=1), commit and halt. If they fail (C=0), branch to skip and return without committing. That's it. The BCC/BCS pattern carries over directly from the real 6502. Carry set means success, carry clear means failure.

A Real Triage Session

Here's drain-the-swamp.s which drains all bug-labeled issues using the todo stack:

        .ORG    $0600

        LDA     #$01        ; label mask: bug
        STA     $20         ; set label filter
        JSR     FETCH       ; populate $10–$1F with issue IDs

; Push fetched issues onto the todo stack
        LDX     #$00
push:   LDA     $10,X       ; load Xth fetched issue
        BEQ     drain       ; empty slot → start draining
        PHA                 ; push as todo
        INX
        CPX     #$10        ; queue bounds
        BNE     push

; Drain the stack: work each issue, skip on failure
drain:  PLA                 ; pop newest → A (zero = empty)
        BEQ     done
        JSR     ANALYZE
        JSR     FIX
        JSR     TEST
        BCC     drain       ; failed → skip, next todo
        JSR     REVIEW
        BCC     drain       ; concerns → skip
        BRK                 ; commit this one
        JMP     drain       ; keep going

done:   JSR     PUSH        ; open PRs for committed branches
        RTS

This loops through every bug issue, tries to fix each one and only commits the ones where tests pass and the self-review is clean. Failed fixes get skipped. At the end it opens PRs for everything that worked. The PHA/PLA cycle maps directly onto Claude Code's task list so each pushed issue becomes a real tracked todo.

What about tokens?

I expected the tight assembly output to translate to substantial cost savings versus prose Claude. The story turned out more nuanced.

I ran a small experiment against a fixture repo with one bug. A 5-line peek program (FETCH issue, ANALYZE, halt), executed five times within a single Claude Code session on Sonnet 4.6. Then the equivalent prose prompt — "look at issue #1, identify the bug, walk me through the fix" — five times in another session. Same model, same fixture, same task scope.

5 invocations, within-session Cost per invocation Output tokens / invocation
Opcode $0.031 ~355
Prose $0.029 ~538

Roughly tied. Prose was actually fractionally cheaper per invocation on this small task.

The reason is asymmetric overhead. Opcode's skill documentation (around 11,000 tokens of SKILL.md, ISA.md and OPCODES.md) sits in the cached prefix on every turn. Across the 11 assistant turns in the session, that's roughly 88k extra cached input tokens served back. Sonnet on prose was already terse on this task — about 540 output tokens per invocation, not the 1,300+ I'd hand-waved when I started. The output savings opcode delivered (around 180 tokens per invocation) didn't quite cover the cost of carrying the skill docs.

For small, deterministic tasks like this one, the orchestration overhead dominates the work — like running a CI pipeline to compile a single file. Opcode probably comes out ahead on larger programs with more decision points (multi-issue queue walks, longer reasoning chains where prose Claude would actually ramble). I haven't measured those yet. The honest claim is workload-dependent: structure may save you tokens at scale; on small one-shots it's roughly a wash.

One thing the data did show clearly: within-session cache leverage is huge. Both opcode and prose runs were ~8× cheaper per invocation than running the same task in fresh, separate sessions. That's Anthropic's prompt cache amortising shared context across turns — and it's the strongest argument for the pipeline framing. Multi-task batches in one persistent context cost cents apiece; fresh-session one-offs cost dimes apiece. Programs are for pipelines isn't a token-savings claim, it's a workflow-shape claim — and the cache math reinforces it for either mode.

The Constraint Is the Feature

There's a deeper thing going on here. The 6502 aesthetic isn't just nostalgic decoration, it's a forcing function. When your output format is assembly you commit to a verb sequence before execution instead of wandering through chat mode. The resulting traces scan way faster than prose. They're diffable, greppable and versionable. You can commit a .s file alongside your code and re-run it on the next batch of issues.

The temptation to add "just one sentence of context" is the whole failure mode. Resist it absolutely.

The skill is pretty militant about this. Claude's response must be a valid .s program. No greetings, no sign-offs, no "Let me", no markdown headers. If it doesn't fit as an instruction, a directive or a semicolon comment it doesn't get said. There are escape hatches like .ASK for questions (≤60 chars), .NOTE for observations (≤80 chars) and .ERR for errors. But these are pressure-release valves, not invitations to prose.

Same Verbs, Bigger Nouns

Here's the bit that stopped being a joke about halfway through. In 1975 a 6502 programmer spent their day loading bytes into registers, comparing them and branching on the result. Load, store, compare, branch. That was the entire job. The 6502 had 56 opcodes, which is why this port even works as an output format — you can hold the whole thing in your head, which x86 and ARM programmers genuinely cannot.

Forty years later I'm writing LDA #$2A to load issue 42, which arrives with a description, a thread of clarifying comments, a set of labels, screenshots Claude can actually see with vision and a graph of linked PRs. The verbs haven't changed. The nouns got about six orders of magnitude bigger. The "address" is an issue ID, the "memory" is GitHub, the "byte" is a self-contained task package. Every byte counted in 1975 because RAM was expensive. Every token counts in 2026 for exactly the same reason. I didn't plan any of that — I was trying to see how far you could push the cosplay — but it turns out the 6502 programmer's habits were always going to travel well.

The Extended ISA: For Completeness and Nostalgia

Because the joke demands it there's a full extended layer (~40 more mnemonics) you can opt into with .EXTENDED ON. Shifts become priority promotions (ASL A = "promote priority"). Logic ops become label-filter algebra (AND #imm = "intersect label mask"). BVS branches on merge conflict. Most of these are tagged as metaphor so they get narrated in the trace but not actually executed.

And because the joke truly demands it there are six illegal opcodes behind .UNSAFE ON. The real undocumented 6502 ops like LAX, SAX and DCP. Pure flavor. Narrated, never executed, not even with the directive set. They exist because "a museum exhibit behind glass" is funnier than not having them at all.

So Is This Actually Useful?

Genuinely, yes. If you run batch triage workflows like scanning a backlog, fixing straightforward bugs and opening PRs then the token savings are real and the structured output is way easier to read than prose. The .s files are reviewable artifacts. The traces are audit logs. And the constraint of planning your workflow as a sequence of opcodes before execution turns out to be surprisingly good discipline.

Is it the most practical way to interact with an AI? No. Would I recommend it for someone who just wants Claude to fix a bug? Also no. But if you're running the same triage pattern across many issues and you care about token costs and you happen to think "commit and halt" beats "I'll now commit these changes to the repository" then this might be your thing.

And it dockerizes trivially for CI use. A 30-line Dockerfile with Node, git and gh, the skill mounted at ~/.claude/skills/opcode/, the target repo mounted as a volume, a .s program passed as the entry. Nightly job fires, drains the queue, opens PRs, exits. The trace is your audit log.

Prompts are for conversations. Programs are for pipelines.

At the end of the day the question is the same one it's always been. Are you a quiche eater or a Real Programmer? Real Programmers don't need prose. They need opcodes, a carry flag and a BRK at the end.

Try it yourself: The skill is called opcode. Drop it into your .claude/skills/ directory, point it at a repo with some open issues and run the oneshot example in dry-run mode. Every program ends the same way: BRK. Commit the work. Halt the machine.
